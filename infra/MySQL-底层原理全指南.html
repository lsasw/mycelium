索引原理

索引是 MySQL 高效查询的基石。理解索引底层数据结构，是写出高性能 SQL 的前提。InnoDB 使用 B+Tree 作为默认索引结构，这一选择直接决定了索引的查找效率、范围查询能力和磁盘 I/O 特性。

1.1 B+Tree 数据结构

为什么选择 B+Tree？

数据库索引需要同时支持 等值查询 和 范围查询，且数据存储在磁盘上，必须最小化 I/O 次数。常见的索引结构对比如下：

数据结构等值查询范围查询磁盘 I/O插入/删除MySQL 使用
HashO(1) 极快✗ 不支持O(1)O(1)Memory 引擎、自适应 Hash
二叉搜索树O(log n)O(log n + k)高（树高过大）O(log n)✗ 不适用
B-TreeO(log n)需回溯低（矮胖）O(log n)✗
B+TreeO(log n)O(log n + k) 极优最低O(log n)✔ InnoDB/MyISAM

B+Tree 核心特征

  • 所有数据存储在叶子节点：非叶子节点只存 key，不存 data，因此一个节点能容纳更多 key，树更"矮胖"
  • 叶子节点形成有序双向链表：支持高效的范围查询（无需回溯父节点）
  • 每个节点对应一个磁盘页（默认 16KB）：一次 I/O 加载一整个节点
  • 树高极低：通常 2~4 层，每层一次 I/O，百万级数据只需 2~3 次 I/O
B+Tree 三层结构：根节点和内部节点只存索引 key（非叶子节点），叶子节点存储完整数据行，并通过双向指针串联以支持范围查询
💡 磁盘 I/O 估算 假设一条索引记录 16 字节，磁盘页 16KB，每个非叶子节点可存约 16KB / 16B ≈ 1000 个 key。3 层 B+Tree 最多容纳 1000 × 1000 × 1000 = 10 亿 条记录，只需 3 次 I/O。
1.2 聚簇索引 vs 二级索引

聚簇索引 (Clustered Index)

  • 叶子节点直接存储完整数据行
  • 每张表有且仅有一个聚簇索引（通常是主键）
  • 主键查询性能最优：一次 B+Tree 搜索直达数据
  • InnoDB 自动选择主键作为聚簇索引；无主键则选唯一非空索引；都没有则生成隐藏 row_id

二级索引 (Secondary Index)

  • 叶子节点存储的是索引列 + 主键值（不存完整行）
  • 一张表可以有多个二级索引
  • 查询需要回表：先在二级索引找到主键，再用主键去聚簇索引查完整行
  • 回表代价高：多一次 B+Tree 搜索（多一次随机 I/O）
聚簇索引叶子存完整行，二级索引叶子只存主键。非覆盖索引查询需"回表"——多一次随机 I/O
1.3 索引查找过程

等值查询 SELECT * FROM users WHERE id = 1003

从根节点开始 → 比较 id=1003 与节点内 key 区间 → 确定下一层子节点 → 重复比较直到叶子节点 → 在叶子节点二分查找 id=1003 → 找到，返回完整行数据（聚簇索引直接拿到 data） 复杂度：O(log n)，通常 2~3 次磁盘 I/O

范围查询 SELECT * FROM users WHERE id BETWEEN 1000 AND 2000

先等值定位到 id=1000 → 沿叶子节点双向链表 → 顺序扫描至 id > 2000 → 停止 → 返回所有匹配行 复杂度：O(log n + k)，k 为结果集大小
⚠ 主键设计建议 自增主键（AUTO_INCREMENT）是最优选择：插入时直接在链表尾部追加，无需页分裂；UUID 或随机主键会导致频繁的页分裂和页填充率降低，严重影响写入性能和空间利用率。

索引原理 · 记忆要点

  • InnoDB 使用 B+Tree——非叶子节点只存 key，叶子节点存数据 + 双向链表
  • 聚簇索引叶子节点存完整行数据，一张表只有一个
  • 二级索引叶子节点存主键值，查完整行需要回表
  • 自增主键最优，避免页分裂；UUID 主键是性能杀手
  • 3 层 B+Tree 可索引 10 亿行，只需 2~3 次 I/O

索引优化

2.1 覆盖索引 (Covering Index)

核心思想

当查询的所有列都在同一个索引中时，无需回表查聚簇索引，直接从二级索引拿到结果。这是性能优化的第一优先手段。

SQL
-- ❌ 需要回表：idx_age 只索引了 age，SELECT * 需要全部列
SELECT * FROM users WHERE age = 25;

-- ✔ 覆盖索引：idx_age_name 索引了 (age, name)，无需回表
CREATE INDEX idx_age_name ON users(age, name);
SELECT age, name FROM users WHERE age = 25;

-- ✔ 使用 EXPLAIN 验证，Extra 列会显示 Using index
EXPLAIN SELECT age, name FROM users WHERE age = 25;
✔ Using index 判断方法 执行 EXPLAIN 后，Extra 列出现 Using index 即表示使用了覆盖索引，这是最优的查询方式。如果出现 Using index condition 则是索引下推（见 2.3）。
⚠ SELECT * 是覆盖索引的敌人 SELECT * 几乎不可能被覆盖索引优化（除非索引包含所有列）。在生产环境应明确列出需要的列。
2.2 最左前缀原则

联合索引的匹配规则

联合索引 (a, b, c) 按列顺序构建 B+Tree：先按 a 排序，a 相同再按 b 排序，b 相同再按 c 排序。因此索引从左到右匹配，跳过中间列则后续列失效。

查询条件是否使用索引原因
WHERE a = 1 AND b = 2 AND c = 3✔ 完全匹配三列全部命中
WHERE a = 1 AND b = 2✔ 匹配 a, b前缀命中
WHERE a = 1 AND c = 3⚠ 仅匹配 ab 缺失，c 无法使用
WHERE b = 2 AND c = 3✗ 全表扫描缺少 a，索引完全失效
WHERE a = 1 AND b > 2 AND c = 3⚠ 匹配 a, b(range)范围查询 b 之后的 c 失效
WHERE a = 1 AND b LIKE 'x%'✔ 匹配 a, bLIKE 'x%' 相当于范围，可用前缀
WHERE a = 1 AND b LIKE '%x'✗ 仅匹配 aLIKE '%x' 前缀模糊，b 失效
SQL
-- 联合索引
CREATE INDEX idx_a_b_c ON orders(user_id, status, create_time);

-- ✔ 走 idx_a_b_c
SELECT * FROM orders WHERE user_id = 100 AND status = 'paid';

-- ✔ 走 idx_a_b_c（范围后 status 也失效）
SELECT * FROM orders WHERE user_id = 100 AND create_time > '2024-01-01';

-- ✔ 走 idx_a_b_c（ORDER BY 也可利用索引有序性）
SELECT * FROM orders WHERE user_id = 100 ORDER BY status;

-- ✗ 不走索引：缺少 user_id
SELECT * FROM orders WHERE status = 'paid';
💡 ORDER BY / GROUP BY 也受最左前缀约束 联合索引 (a, b) 下，WHERE a = 1 ORDER BY b 可以用索引排序；WHERE a = 1 ORDER BY c 则需要 filesort。
2.3 索引下推 (ICP, Index Condition Pushdown)

MySQL 5.6+ 的优化利器

传统流程中，存储引擎只按索引条件过滤，剩余条件交给 Server 层处理——这意味着不符合全部条件的行也要回表。ICP 将部分 WHERE 条件下推到存储引擎层，在索引层面就过滤掉不满足条件的行，减少回表次数。

ICP 在索引层面预先过滤，减少回表次数，尤其适合联合索引中前面列做范围查询的场景

2.5 EXPLAIN 执行计划解读

EXPLAIN 核心列速查

通过 EXPLAIN 可以精确判断查询是否用了索引、访问了多少行、是否使用了临时表或文件排序。

列名含义需要关注的值
type访问类型（越靠前越好）system > const > eq_ref > ref > range > index > ALL
key实际使用的索引NULL = 未使用索引，需要排查
key_len使用的索引长度越小越好，可判断联合索引用了几列
rows预估扫描行数越小越好，是优化器估算值
Extra附加信息Using index（覆盖索引）/ Using filesort（需优化）/ Using temporary（需优化）/ Using where（Server 层过滤）/ Using index condition（ICP）
possible_keys可能使用的索引列表中的索引都可能被用上
ref索引匹配的列或常量const = 常量匹配，列名 = 关联匹配
SQL
-- type=ALL, 全表扫描，需要加索引
EXPLAIN SELECT * FROM users WHERE name = '张三';
-- type: ALL | key: NULL | rows: 100000 | Extra: Using where

-- type=ref, 非唯一索引查找
EXPLAIN SELECT * FROM users WHERE age = 25;
-- type: ref | key: idx_age | rows: 500 | Extra: NULL

-- type=range, 范围扫描
EXPLAIN SELECT * FROM orders WHERE create_time >= '2024-01-01';
-- type: range | key: idx_ctime | rows: 10000 | Extra: Using index condition

-- type=const, 主键或唯一索引等值查询（最优）
EXPLAIN SELECT * FROM users WHERE id = 1003;
-- type: const | key: PRIMARY | rows: 1 | Extra: NULL
💡 EXPLAIN ANALYZE (MySQL 8.0.18+) 比 EXPLAIN 更精确，它会实际执行查询并输出每一步的真实耗时和行数，格式为树状结构。调试慢查询首选。

索引优化 · 记忆要点

  • 覆盖索引避免回表，是最高效的优化手段（EXPLAIN 看 Using index）
  • 最左前缀：联合索引 (a,b,c) 跳 a 则 b/c 全失效
  • ICP 索引下推：MySQL 5.6+，存储引擎层预过滤，减少回表
  • 索引失效 7 大场景：函数运算、类型转换、前置 %、OR 混用、!=、最左缺失、IS NULL
  • EXPLAIN：关注 type（避免 ALL）、key（是否用到索引）、Extra（Using filesort/temporary 需优化）

事务与锁机制

3.1 ACID 特性

A — 原子性 (Atomicity)

事务是不可分割的最小单元，要么全部成功，要么全部失败回滚。由 Undo Log 保证。

C — 一致性 (Consistency)

事务前后数据必须满足所有约束（主键、外键、NOT NULL 等）。由 A+I+D 共同保证。

I — 隔离性 (Isolation)

并发事务之间互相隔离，互不干扰。由 MVCC + 锁 保证。

D — 持久性 (Durability)

事务一旦提交，数据永久保存，即使系统崩溃也不丢失。由 Redo Log 保证。

各特性对应机制

特性核心机制作用
原子性Undo Log回滚时恢复数据到事务开始前的状态
隔离性MVCC + 锁并发控制，避免事务间互相干扰
持久性Redo Log崩溃恢复，确保已提交数据不丢失
一致性以上三者 + 约束数据完整性由 A+I+D 联合保障
3.2 MVCC 多版本并发控制

MVCC 核心机制

MVCC（Multi-Version Concurrency Control）通过维护数据的多个版本，让读操作不加锁、不阻塞写操作，写操作也不阻塞读操作。这是 InnoDB 实现高并发读写的关键。

MVCC 四大组件

  • 隐藏列：每行有 DB_TRX_ID（最近修改的事务 ID）、DB_ROLL_PTR（回滚指针，指向 Undo Log）、DB_ROW_ID（无主键时用）
  • Undo Log 版本链：每次修改生成一条 Undo Log，通过 DB_ROLL_PTR 串联成历史版本链
  • ReadView：快照读时生成，决定了当前事务能看到哪些版本。包含 m_ids（活跃事务列表）、min_trx_id（最小活跃事务 ID）、max_trx_id（下一个待分配的事务 ID）、creator_trx_id（当前事务 ID）
  • 可见性判断：根据 ReadView 和行版本的 DB_TRX_ID 判断该版本是否对当前事务可见
MVCC 通过 Undo Log 版本链 + ReadView 实现无锁的快照读。RC 每次读生成新 ReadView，RR 整个事务共用同一个 ReadView

三种并发问题图解

  • 脏读：事务 A 读到事务 B 未提交的修改。B 回滚后 A 读到的数据是"脏"的
  • 不可重复读：事务 A 内两次读同一行，结果不同（因为 B 在两次读之间修改并提交了该行）
  • 幻读：事务 A 内两次范围查询，结果集行数不同（因为 B 在两次读之间插入了新行）
SQL
-- 查看当前隔离级别
SELECT @@transaction_isolation;

-- 设置隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 不可重复读演示（RC 级别）
-- 事务 A                          事务 B
BEGIN;                            BEGIN;
SELECT name FROM users            -- name='张三'
  WHERE id = 1;
                                  UPDATE users SET name='李四' WHERE id = 1;
                                  COMMIT;
SELECT name FROM users            -- name='李四'（RC 下读到了 B 的提交）
  WHERE id = 1;
COMMIT;
3.4 锁机制全景

行锁

锁定具体行记录
并发度最高
基于索引加锁

间隙锁

锁定索引记录间隙
防止幻读（插入）
RR 级别自动添加

表锁

锁定整张表
DDL 操作 / MyISAM
并发度最低

行锁类型（InnoDB）

  • 共享锁（S 锁 / 读锁）：SELECT ... LOCK IN SHARE MODE（MySQL 8.0: FOR SHARE）。允许其他事务读，不允许写。S 锁之间兼容。
  • 排他锁（X 锁 / 写锁）：SELECT ... FOR UPDATE 或 DML 语句自动加。与任何其他锁互斥。
  • 意向锁（IS / IX）：表级锁，表明事务打算在表中的行上加 S/X 锁。用于快速判断表是否与表锁冲突。
  • 记录锁（Record Lock）：锁定单行索引记录。
  • 间隙锁（Gap Lock）：锁定索引记录之间的间隙，防止插入，解决幻读。RR 级别下自动添加。
  • 临键锁（Next-Key Lock）：记录锁 + 间隙锁 的组合，InnoDB 默认的行锁算法。锁住索引记录及其前间隙。

-- 查看当前锁信息（MySQL 8.0）

-- 查看锁等待
SELECT * FROM performance_schema.data_lock_waits;

-- 查看当前事务

-- 死锁检测（InnoDB 默认开启，自动回滚代价最小的事务）

-- 排他锁示例：锁定 id=1 的行，其他事务无法写
BEGIN;
SELECT * FROM users WHERE id = 1 FOR UPDATE;
-- ...业务操作...
COMMIT;
⚠ 死锁预防
  1. 按固定顺序访问资源（所有事务先锁 A 再锁 B）
  2. 缩短事务时间，尽早提交
  3. 合理使用索引（无索引会导致行锁升级为表锁）
  4. 设置 innodb_lock_wait_timeout 避免无限等待

事务与锁 · 记忆要点

  • ACID：原子性(Undo Log) / 一致性(约束+AID) / 隔离性(MVCC+锁) / 持久性(Redo Log)
  • MVCC = 隐藏列(DB_TRX_ID+DB_ROLL_PTR) + Undo Log 版本链 + ReadView + 可见性判断
  • RC vs RR：RC 每次 SELECT 新 ReadView（不可重复读），RR 首次 SELECT 生成 ReadView（可重复读）
  • 锁：行锁（S/X）→ 间隙锁（防幻读）→ 临键锁（行锁+间隙锁，InnoDB 默认）
  • 默认隔离级别 RR，已解决脏读/不可重复读/大部分幻读

InnoDB 存储引擎

InnoDB 是 MySQL 的默认存储引擎，通过 Buffer Pool 缓存热点数据减少磁盘 I/O，通过 Redo Log + Undo Log + Binlog 三大日志体系保证事务的原子性和持久性。

4.1 Buffer Pool 缓冲池

什么是 Buffer Pool？

InnoDB 在内存中开辟的一块连续内存区域，用于缓存数据页和索引页。所有读写操作首先访问 Buffer Pool，命中则直接返回，未命中则从磁盘加载。这是 InnoDB 最核心的性能组件。

核心特性

  • 默认大小：128MB（建议设为物理内存的 50%~80%），参数 innodb_buffer_pool_size
  • 页（Page）：Buffer Pool 的最小管理单位，默认 16KB
  • LRU 链表：分 Young（5/8，热数据）和 Old（3/8，冷数据）两个子链表。新读入的页先放入 Old 区头部，再次访问时移到 Young 区。防止全表扫描污染热数据
  • Free 链表：管理空闲页
  • Flush 链表：管理脏页（内存中修改过但未刷盘的页）
  • 自适应 Hash 索引：对频繁访问的索引页自动建立 Hash 索引，加速等值查询
  • Change Buffer：对非唯一二级索引的插入/更新操作先缓存在内存，异步合并。减少随机 I/O
Buffer Pool 内存架构：LRU 双区链表 + Free/Flush 链表 + 自适应 Hash + Change Buffer
4.2 Redo Log（重做日志）

作用：崩溃恢复，保证持久性

Redo Log 是 InnoDB 引擎层的物理日志，记录"对哪个数据页的哪个位置做了什么修改"。采用 WAL（Write-Ahead Logging）策略：先写日志，再写磁盘。

如果每次更新都直接写磁盘，就是随机 I/O，性能极差。Redo Log 是顺序追加写入，性能远高于随机写。数据页的刷盘则可以延迟、批量进行。

核心概念

  • 固定大小、循环写：由 innodb_log_file_size × innodb_log_files_in_group 决定总大小（默认 48MB × 2 = 96MB，生产建议 1~4GB）
  • 两个文件交替写：ib_logfile0 和 ib_logfile1
  • LSN（Log Sequence Number）：单调递增的日志编号，全局唯一，标识 Redo Log 的写入位置
  • Checkpoint：当脏页刷盘后，对应的 Redo Log 可以被覆盖。Checkpoint LSN 之前的日志已不再需要
  • 刷盘策略：innodb_flush_log_at_trx_commit
    • = 1（默认，最安全）：每次提交都刷盘
    • = 2：每次提交写 OS 缓存，每秒刷盘
    • = 0：每秒刷盘一次（性能最好但可能丢失 1 秒数据）
Redo Log 循环写：write pos 和 checkpoint 之间的区域是已写入的部分。checkpoint 推进后前面的空间可复用
4.3 Undo Log（回滚日志）

两大作用

  • 事务回滚：记录数据修改前的旧值，ROLLBACK 时根据 Undo Log 将数据恢复到事务开始前的状态
  • MVCC 快照读：通过 Undo Log 构建历史版本链，使读操作能访问到事务开始时的数据版本

核心概念

  • 逻辑日志：记录的是 SQL 的逆操作（INSERT 对应 DELETE，UPDATE 对应反向 UPDATE，DELETE 对应 INSERT）
  • 存储位置：Undo Tablespace（默认在共享表空间 ibdata1，MySQL 8.0 支持独立 Undo 表空间）
  • Undo 页链表：每个事务的 Undo Log 通过 DB_ROLL_PTR 链式连接
  • purge 线程：当事务提交后，Undo Log 不再需要用于回滚，但如果还有 ReadView 在引用就还不能删除。purge 线程定期清理不再被任何 ReadView 需要的 Undo Log
  • 长事务的危害：长事务会阻止 Undo Log 清理，导致 Undo 表空间膨胀
4.4 Binlog（归档日志）
对比维度Redo LogBinlog
所属层InnoDB 引擎层MySQL Server 层
日志类型物理日志（页级修改）逻辑日志（SQL 语句或行变更）
写入方式循环写，固定大小追加写，文件不断增长
主要用途崩溃恢复（crash-safe）主从复制、数据恢复、审计
刷盘参数innodb_flush_log_at_trx_commitsync_binlog

Binlog 三种格式

  • STATEMENT：记录 SQL 语句本身。体积小，但某些函数（NOW()、UUID()）在主从环境下结果可能不一致
  • ROW（推荐）：记录每行数据的具体变更。体积大，但最精确、最安全，不会产生主从不一致
  • MIXED：默认 STATEMENT，特殊情况下自动切换为 ROW。折中方案
4.5 更新语句完整写入流程

UPDATE users SET name='王五' WHERE id=1 的执行全流程

1. 执行器 调用 InnoDB 接口，搜索 id=1 的数据行 2. 数据页在 Buffer Pool 中？是 → 直接使用；否 → 从磁盘加载 3. 将目标行加 X 锁（排他锁），防止其他事务并发修改 4. 将旧值写入 Undo Log（用于回滚 + MVCC） 5. 修改 Buffer Pool 中的数据页（name='张三' → '王五'），页变为脏页 6. 将修改操作写入 Redo Log（prepare 阶段） 7. Server 层写 Binlog 8. Redo Log 提交（commit 阶段）—— 这就是两阶段提交 9. 事务提交成功，返回客户端 10. 后台线程异步将脏页刷入磁盘（不阻塞事务提交）
两阶段提交：Prepare (Redo) → 写 Binlog → Commit (Redo)，保证两个日志的一致性

InnoDB 存储引擎 · 记忆要点

  • Buffer Pool：内存缓存数据页和索引页，LRU 分 Young/Old 区防污染，Change Buffer 优化非唯一二级索引写
  • Redo Log：循环写物理日志 → 崩溃恢复（WAL），写 Redo 是顺序 I/O 远快于随机写磁盘
  • Undo Log：逻辑日志 → 事务回滚 + MVCC 构建历史版本链
  • Binlog：Server 层逻辑日志 → 主从复制 + 数据恢复，推荐 ROW 格式
  • 两阶段提交：Prepare (Redo) → Binlog → Commit (Redo)，保证两者一致
  • 生产配置：innodb_flush_log_at_trx_commit=1 + sync_binlog=1

分库分表知识体系

当单表数据量超过 500 万行或单库 QPS 超过 2000 时，MySQL 单机性能开始遇到瓶颈。分库分表是解决海量数据存储和高并发访问的核心架构手段，但它也带来跨分片查询、分布式事务等一系列挑战。

5.1 为什么需要分库分表

数据量瓶颈

  • 单表超过 2000 万行后 B+Tree 树高增加，查询变慢
  • 索引过大无法全部载入 Buffer Pool，缓存命中率骤降
  • 备份恢复时间线性增长，运维窗口拉长
  • DDL 操作（加字段、建索引）可能锁表数小时

并发压力瓶颈

  • 单库连接数有限（通常 2000~5000），高并发耗尽连接
  • 写入集中在同一张表的同一个数据页，产生热点争用
  • 单机磁盘 I/O 带宽成为瓶颈（即使上了 SSD）
  • 主从延迟随写入量增大而恶化
💡 500 万行还是一亿行？ 没有绝对阈值。核心是要监控：慢查询占比、Buffer Pool 命中率、磁盘 IOPS。通常建议在 1000 万 ~ 2000 万 行时开始规划拆分，而不是等到出问题再救火。
5.2 垂直拆分 vs 水平拆分

垂直拆分（Vertical Sharding）—— 按业务列拆分

将一张宽表的字段按访问频率拆到多张表中。高频字段（如标题、状态）放主表，低频大字段（如正文、附件）放扩展表。

SQL
-- 垂直拆分前：一张大宽表
CREATE TABLE article (
  id BIGINT PRIMARY KEY,
  title VARCHAR(200),      -- 高频：列表页展示
  status TINYINT,           -- 高频
  content TEXT,             -- 低频：只在详情页用
  author_bio TEXT,          -- 低频
  INDEX idx_status(status)
);

-- 垂直拆分后：主表 + 扩展表
CREATE TABLE article_main (
  id BIGINT PRIMARY KEY,
  title VARCHAR(200),
  status TINYINT,
  INDEX idx_status(status)
);
CREATE TABLE article_detail (
  id BIGINT PRIMARY KEY,
  content TEXT,
  author_bio TEXT
);
✔ 垂直拆分优点 主表行变小 → 一个数据页能放更多行 → Buffer Pool 命中率提升 → 列表页查询更快。扩展表只在需要时才 JOIN。

水平拆分（Horizontal Sharding）—— 按行拆分到多个库/表

将同一张表的数据行按某种规则分散到多个库或表中。每个分片结构完全相同，只是数据不同。这是解决海量数据的核心手段。

水平拆分将一张大表的数据分散到多个结构相同的分片中，每个分片独立存储、独立查询

5.5 核心问题与解决方案

1. 跨分片查询

当查询条件不是分片键时，需要扫描所有分片然后合并结果，性能急剧下降。

解决：冗余存储（下单索引表）、ES 做二级索引、尽量让查询带分片键

2. 分布式事务

跨分片操作需要保证 ACID，单机事务不再适用。

解决：Seata AT/TCC 模式、事务消息（RocketMQ）、最终一致性方案

3. 全局唯一 ID

自增主键在各个分片独立增长，会重复。

解决：Snowflake 雪花算法（推荐）、数据库号段模式、Redis 自增、美团 Leaf

4. 数据迁移与扩容

分片数不够时需增加分片，历史数据需要重新分布。

解决：一致性 Hash（减少迁移量）、双写 + 灰度切流、ShardingSphere Scaling

JAVA
// Snowflake 雪花算法 ID 结构（64位）
//   1位符号位 + 41位时间戳 + 10位工作机器ID + 12位序列号
//   = 支持每毫秒 4096 个 ID，分布式唯一且趋势递增

public class SnowflakeId {
    private long workerId;      // 0~31
    private long datacenterId;  // 0~31
    private long sequence = 0L;
    private long lastTimestamp = -1L;

    // 时间起始点：2020-01-01
    private final long twepoch = 1577808000000L;

    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis();
        if (timestamp < lastTimestamp) {
            throw new RuntimeException("Clock moved backwards!");
        }
        if (timestamp == lastTimestamp) {
            sequence = (sequence + 1) & 4095; // 12位序列号
            if (sequence == 0) timestamp = tilNextMillis(lastTimestamp);
        } else {
            sequence = 0L;
        }
        lastTimestamp = timestamp;
        return ((timestamp - twepoch) << 22)   // 时间戳左移22位
             | (datacenterId << 17)              // 数据中心ID左移17位
             | (workerId << 12)                  // 机器ID左移12位
             | sequence;                         // 序列号
    }
}

分库分表 · 记忆要点

  • 拆分时机：单表 1000~2000 万行或 QPS > 2000 时开始规划，看慢查询和 Buffer Pool 命中率
  • 垂直拆分：按列拆宽表，高频字段和低频大字段分离；水平拆分：按行拆大表到多库多表
  • 4 种分片策略：范围（简单但不均）、Hash（均匀但难扩容）、一致性 Hash（易扩容）、复合（租户隔离）
  • 中间件：ShardingSphere（Java SDK）、MyCat（Proxy 透明）、Vitess（云原生 K8s）
  • 4 大核心问题：跨分片查询 → 索引表；分布式事务 → Seata/事务消息；全局 ID → 雪花算法；扩容 → 一致性 Hash + 灰度

生产环境中遇到的 MySQL 问题往往有规律可循。本章按连接认证 → 性能优化 → 事务一致性 → 存储引擎 → 备份恢复五大类梳理高频问题，每个问题给出现象描述 → 原因分析 → 解决方案的完整排查链路。

7.1 连接与认证问题

Q1: Too many connections —— 连接数耗尽

现象：应用报错 ERROR 1040 (HY000): Too many connections，新连接无法建立。

原因：① 连接池配置过大或未释放；② 长连接泄漏（忘记 close）；③ max_connections 设置过低；④ 突发流量打满连接池。

SQL / SHELL
-- 查看当前连接数和上限
SHOW VARIABLES LIKE 'max_connections';      -- 默认 151
SHOW STATUS LIKE 'Threads_connected';       -- 当前活跃连接

-- 查看各客户端连接数
SELECT host, COUNT(*) AS cnt
FROM information_schema.processlist
GROUP BY host ORDER BY cnt DESC;

-- 临时调大（重启失效）
SET GLOBAL max_connections = 500;

-- 永久生效：my.cnf
-- [mysqld]
-- max_connections = 500
-- max_user_connections = 200   -- 单用户上限，防止单应用占满

-- 找到并 KILL 长时间睡眠的连接
SELECT id, user, host, time, command
FROM information_schema.processlist
WHERE command = 'Sleep' AND time > 300;
⚠ 根因排查 调大 max_connections 只是治标。需检查应用连接池配置（如 HikariCP maximumPoolSize）、是否有连接泄漏、是否需要引入 ProxySQL 连接池复用。

Q2: Access denied —— 权限拒绝

现象：报错 ERROR 1045 (28000): Access denied for user 'xxx'@'host'。

原因：① 密码错误；② 用户没有从该 IP 连接的权限；③ host 字段限制（如只允许 localhost）；④ 密码过期（MySQL 5.7+ 默认 360 天过期）。

SQL
-- 查看用户和允许的 host
SELECT user, host, authentication_string
FROM mysql.user WHERE user = 'myuser';

-- 授权特定 IP 访问
CREATE USER 'myuser'@'192.168.1.%' IDENTIFIED BY 'password';
GRANT SELECT, INSERT, UPDATE, DELETE ON mydb.* TO 'myuser'@'192.168.1.%';
FLUSH PRIVILEGES;

-- 密码过期问题：设置永不过期
ALTER USER 'myuser'@'192.168.1.%' PASSWORD EXPIRE NEVER;

-- 忘记 root 密码的恢复流程（需重启 MySQL）
-- 1. my.cnf 添加 skip-grant-tables
-- 2. 重启 MySQL
-- 3. mysql -u root 直接进入
-- 4. ALTER USER 'root'@'localhost' IDENTIFIED BY 'newpass';
-- 5. 移除 skip-grant-tables 并重启

Q3: 中文乱码 —— 字符集问题

现象：写入中文后查询显示 ??? 或乱码。

原因：① 数据库/表/列字符集不是 utf8mb4；② 连接字符集与服务端不一致；③ 使用了已废弃的 utf8（实为 utf8mb3，不支持 4 字节 emoji）。

SQL
-- 查看字符集
SHOW VARIABLES LIKE 'character_set%';
SHOW CREATE TABLE mytable;   -- 看表和列的字符集

-- MySQL 8.0 默认已为 utf8mb4，旧版需手动设置
-- my.cnf
-- [mysqld]
-- character-set-server = utf8mb4
-- collation-server = utf8mb4_unicode_ci
-- [client]
-- default-character-set = utf8mb4

-- 修改已有表的字符集
ALTER TABLE mytable CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- JDBC 连接串指定字符集
-- jdbc:mysql://host:3306/db?useUnicode=true&characterEncoding=utf8mb4
7.2 性能优化问题

Q4: 慢查询定位与优化

现象：接口响应慢，数据库 CPU 飙高。

原因：① 未走索引（全表扫描）；② 索引设计不合理；③ 数据量过大未分表；④ 锁等待；⑤ SQL 写法低效。

SQL / SHELL
-- 开启慢查询日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;          -- 超过 1 秒记录
SET GLOBAL slow_query_log_file = '/var/log/mysql/slow.log';

-- 实时查看正在执行的慢 SQL
SELECT id, user, host, db, command, time, state, info
FROM information_schema.processlist
WHERE time > 2 AND info IS NOT NULL;

-- 用 mysqldumpslow 分析慢日志
-- mysqldumpslow -s t -t 10 /var/log/mysql/slow.log
--   -s t 按总时间排序  -t 10 取前10条

-- 用 EXPLAIN 分析具体 SQL
EXPLAIN SELECT * FROM orders WHERE user_id = 100;
-- 重点看 type(避免ALL) / key(是否用索引) / rows(扫描行数) / Extra
✔ 慢查询优化四步法 ① EXPLAIN 看执行计划 → ② 加/调索引（覆盖索引优先）→ ③ 改 SQL 写法（避免 SELECT *、子查询改 JOIN）→ ④ 考虑分表（数据量超千万）。

Q5: 索引为什么没生效？

现象：建了索引但 EXPLAIN 显示 type=ALL，全表扫描。

原因：参见第 2 章索引失效 7 大场景 —— 函数运算、隐式类型转换、LIKE 前置 %、OR 混用、!= 、最左前缀缺失、IS NULL。

SQL
-- 检查是否真的没用索引
EXPLAIN SELECT * FROM users WHERE phone = 13800138000;
-- phone 是 VARCHAR，传入数字 → 隐式转换 → 索引失效

-- 修复：字符串类型加引号
EXPLAIN SELECT * FROM users WHERE phone = '13800138000';
-- 现在 type=ref, key=idx_phone

-- 强制使用指定索引（调试用，不建议生产常态）
SELECT * FROM users FORCE INDEX(idx_phone) WHERE phone = '13800138000';

-- 检查索引统计信息是否过期（可能导致优化器选错索引）
ANALYZE TABLE users;

Q6: MySQL CPU 100% 怎么排查？

原因：① 慢 SQL 全表扫描消耗 CPU；② 临时表/排序过大（Using filesort / Using temporary）；③ 并发 QPS 突增；④ 缺少索引导致大量回表。

SHELL
# 1. 找到占 CPU 最高的 MySQL 线程
top -H -p $(pgrep mysqld)
# 记录 TID（十进制）

# 2. 在 MySQL 中查看对应 SQL
SELECT thread_id, PROCESSLIST_ID, PROCESSLIST_INFO
FROM performance_schema.threads
WHERE THREAD_OS_ID = ;

# 3. 或直接查 processlist 找耗时最长的
mysql -e "SHOW FULL PROCESSLIST" | sort -t$'\t' -k6 -rn | head

# 4. pt-tools 精准定位（Percona Toolkit）
pt-query-digest /var/log/mysql/slow.log --order-by Query_time:sum
7.3 数据一致性与事务问题

Q7: 死锁 —— Deadlock found when trying to get lock

现象：事务报错 ERROR 1213 (40001): Deadlock found，其中一个事务被自动回滚。

原因：两个事务互相等待对方持有的锁。典型场景：事务 A 先锁行 1 再锁行 2，事务 B 先锁行 2 再锁行 1。

SQL
-- 查看最近一次死锁详情
SHOW ENGINE INNODB STATUS\G
-- 找到 "LATEST DETECTED DEADLOCK" 段落
-- 会显示两个事务各自持有和等待的锁

-- MySQL 8.0 查看死锁监控
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;

-- 查看锁等待超时设置
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';  -- 默认 50 秒
⚠ 死锁预防四原则 ① 固定加锁顺序：所有事务按主键升序加锁
② 缩短事务：事务中不要有 RPC 调用、文件 IO 等慢操作
③ 降低隔离级别：RR → RC 可减少间隙锁
④ 合理索引：无索引会锁表（行锁升级为表锁）

Q8: 主从复制延迟过大

现象：从库数据落后主库数秒甚至数分钟，读写分离后读到旧数据。

原因：① 大事务（一次性写入百万行）；② 从库单线程回放（MySQL 5.6 之前）；③ 从库硬件差于主库；④ 网络延迟；⑤ 从库有慢查询阻塞了 SQL 线程。

SQL
-- 查看主从延迟
SHOW SLAVE STATUS\G
-- 关注：
--   Seconds_Behind_Master: 延迟秒数
--   Slave_IO_Running: Yes/No
--   Slave_SQL_Running: Yes/No

-- MySQL 8.0 性能_SCHEMA 更精确
SELECT * FROM performance_schema.replication_connection_status;
SELECT * FROM performance_schema.replication_applier_status_by_worker;

-- 加速从库回放（MySQL 5.7+ 多线程复制）
-- my.cnf
-- slave_parallel_workers = 8
-- slave_parallel_type = LOGICAL_CLOCK
-- slave_preserve_commit_order = ON
💡 读写分离的一致性方案 关键业务（如订单创建后立即查询）可以：① 写主库后强制读主库（一定时间窗口内）；② 使用 WAIT / semi-sync 半同步复制确保从库已收到日志再返回。

Q9: RR 隔离级别下还会出现幻读吗？

现象：理论上 RR 已解决幻读，但在当前读场景下可能仍有问题。

原因：RR 的 MVCC 只对快照读（普通 SELECT）生效。当前读（SELECT ... FOR UPDATE / UPDATE / DELETE）读取最新数据，需要间隙锁来防止幻读。如果只用快照读而不加锁，在事务中途其他事务插入数据后再做当前读，可能看到新行。

SQL
-- 事务 A (RR)                    事务 B
BEGIN;                            BEGIN;
SELECT * FROM orders              -- 快照读，看到 100 行
  WHERE amount > 100;
                                  INSERT INTO orders(amount)
                                  VALUES(200);  -- 插入新行
                                  COMMIT;
SELECT * FROM orders              -- 快照读，仍然 100 行 ✔
  WHERE amount > 100;
SELECT * FROM orders              -- 当前读，看到 101 行 ⚠ 幻读!
  WHERE amount > 100 FOR UPDATE;
COMMIT;

-- 解决：需要防幻读时用 FOR UPDATE 加间隙锁
BEGIN;
SELECT * FROM orders
  WHERE amount > 100 FOR UPDATE;  -- 加临键锁，阻止插入
-- 此时事务 B 的 INSERT 会被阻塞
COMMIT;

Q11: 表碎片整理 —— 空间不释放

现象：大量 DELETE 后表文件大小没减小，磁盘空间未回收。

原因：InnoDB 删除数据后只是标记为可复用，物理空间不会自动归还操作系统，产生碎片。

SQL
-- 查看碎片率
SELECT
  table_name,
  ROUND(data_length/1024/1024, 2) AS data_mb,
  ROUND(index_length/1024/1024, 2) AS index_mb,
  ROUND(data_free/1024/1024, 2) AS free_mb,
  ROUND(data_free/(data_length+index_length)*100, 1) AS frag_pct
FROM information_schema.tables
WHERE table_schema = 'mydb'
ORDER BY free_mb DESC;

-- OPTIMIZE TABLE：重建表回收碎片（锁表，慎用大表）
OPTIMIZE TABLE mytable;

-- MySQL 8.0 推荐：在线 DDL 重建（不锁表）
ALTER TABLE mytable ENGINE=InnoDB;

-- pt-online-schema-change（Percona，零停机）
-- pt-online-schema-change --alter "ENGINE=InnoDB" D=mydb,t=mytable

Q12: 为什么 InnoDB 查询也被锁住了？

现象：明明用的 InnoDB，SELECT 却被阻塞等待。

原因：① 查询条件未走索引，行锁升级为表锁；② LOCK IN SHARE MODE / FOR UPDATE 加了显式锁；③ 隔离级别为 SERIALIZABLE，所有 SELECT 自动加共享锁；④ DDL 操作（ALTER TABLE）触发了 MDL 锁。

SQL
-- 查看当前锁等待
SELECT
  r.trx_id AS waiting_trx,
  r.trx_query AS waiting_sql,
  b.trx_id AS blocking_trx,
  b.trx_query AS blocking_sql,
  TIMESTAMPDIFF(SECOND, r.trx_wait_started, NOW()) AS wait_sec
FROM information_schema.innodb_trx r
JOIN information_schema.innodb_locks w ON r.trx_id = w.lock_trx_id
JOIN information_schema.innodb_locks b ON w.lock_table = b.lock_table
JOIN information_schema.innodb_trx b ON b.trx_id = b.lock_trx_id;

-- KILL 阻塞源头
KILL ;

-- 检查是否有未走索引的查询（processlist 中 time 值大的）
SHOW FULL PROCESSLIST;
7.5 备份与恢复问题

Q13: mysqldump vs Percona XtraBackup 选哪个？

维度mysqldumpPercona XtraBackup
类型逻辑备份（SQL 语句）物理备份（数据文件拷贝）
速度慢（需执行 SQL 重建）快（直接拷文件）
体积文本文件，可压缩与原库相当
一致性--single-transaction 一致性快照基于 Redo Log 保证一致
锁影响InnoDB 无锁，MyISAM 锁表几乎无锁
恢复速度慢（逐条执行 SQL）快（拷回文件 + crash recovery）
适用小库 / 跨版本迁移 / 单表导出大库（100GB+）/ 快速恢复
SHELL
# mysqldump 逻辑备份（小中型库）
mysqldump -u root -p \
  --single-transaction \         # InnoDB 一致性快照（不锁表）
  --routines \                   # 包含存储过程
  --triggers \                   # 包含触发器
  --set-gtid-purged=OFF \        # 不带 GTID 信息
  --databases mydb > backup.sql

# 恢复
mysql -u root -p mydb < backup.sql

# Percona XtraBackup 物理备份（大型库）
xtrabackup --backup --target-dir=/backup/full \
  --user=root --password=xxx

# 准备备份（应用 Redo Log 使一致性）
xtrabackup --prepare --target-dir=/backup/full

# 恢复（需先停止 MySQL）
xtrabackup --copy-back --target-dir=/backup/full
chown -R mysql:mysql /var/lib/mysql
systemctl start mysqld

# 3. 导入到生产库

Q15: 如何做基于时间点的恢复（PITR）？

场景：凌晨 2 点全量备份，上午 10 点误删表，需要恢复到 9:59 的状态。

SHELL
# PITR (Point-In-Time Recovery) 三步走

# 步骤 1: 恢复全量备份（到凌晨 2 点状态）
xtrabackup --copy-back --target-dir=/backup/full_2am
systemctl start mysqld

# 步骤 2: 回放 binlog 到误操作前（2:00 ~ 9:59）
mysqlbinlog --start-datetime="2026-07-26 02:00:00" \
            --stop-datetime="2026-07-26 09:59:00" \
  /var/lib/mysql/mysql-bin.000124 \
  /var/lib/mysql/mysql-bin.000125 \
  | mysql -u root -p

# 步骤 3: 验证数据完整性后切换应用连接
# 如需精确到某个 SQL 语句：
#   先用 mysqlbinlog 查看 --stop-position 的具体位置
mysqlbinlog --start-datetime="2026-07-26 09:55:00" \
  /var/lib/mysql/mysql-bin.000125 | less
# 找到误删语句前的 --stop-position=12345
mysqlbinlog --start-datetime="2026-07-26 02:00:00" \
            --stop-position=12345 \
  /var/lib/mysql/mysql-bin.000125 | mysql -u root -p

常见问题 FAQ · 记忆要点

  • 连接耗尽：查 processlist + 调 max_connections + 排查连接池泄漏
  • 慢查询：slow_query_log + EXPLAIN 四步法（看计划→加索引→改SQL→分表）
  • 死锁：SHOW ENGINE INNODB STATUS 看详情，固定加锁顺序 + 缩短事务
  • 主从延迟：多线程复制 + 避免大事务 + 关键路径强制读主
  • InnoDB vs MyISAM：InnoDB 支持事务+行锁+崩溃恢复，MyISAM 已不推荐
  • 误删恢复：Binlog 闪回（ROW 格式） > 全量备份恢复 > 延迟从库
  • PITR：全量备份 + binlog 回放到指定时间点/位置
  • 预防 > 恢复：开 binlog + 定期备份 + sql_safe_updates + 延迟从库

全篇核心知识链路

索引（B+Tree → 聚簇/二级 → 回表）→ 优化（覆盖索引/最左前缀/ICP/EXPLAIN） → 事务（ACID → MVCC + ReadView → RR 默认隔离）→ 锁（行锁/间隙锁/临键锁 → 防幻读） → 持久化（Buffer Pool 缓存 → Redo Log WAL → 两阶段提交 → Binlog 复制） → 分库分表（垂直/水平拆分 → Hash/一致性Hash 分片 → ShardingSphere → 雪花ID/跨分片查询） → 数据库选型（MySQL vs PG vs Oracle → NoSQL 六大门派 → 混合架构 NewSQL） → FAQ（连接认证 → 慢查询优化 → 死锁排查 → 误删恢复 → PITR）

一句话总结：用 B+Tree 高效查数据，用 MVCC 无锁并发读，用 Redo/Undo/Binlog 三大日志保证事务 ACID， 用两阶段提交协调 Redo 与 Binlog 一致；当单机扛不住时，用分库分表横向扩展；面对不同场景时，选择最匹配的数据库组合； 遇到生产问题时，按「现象 → 原因 → 方案」的系统化排查链路快速定位——这就是现代 MySQL 开发者必备的完整知识体系。
