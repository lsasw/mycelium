1 📋 需求调研

需求调研是整个 RAG 智能客服项目的基础。这一阶段需要明确「为谁服务、解决什么问题、达到什么效果」三个核心命题，直接决定后续技术选型和数据策略方向。

1.1 核心业务场景

智能客服的核心价值在于降低人力成本的同时保持服务质量。不同业务场景对 RAG 系统的要求差异很大，必须在调研阶段明确优先级。

💬

FAQ 问答

单轮知识检索型问答。用户提出问题，系统从知识库检索最相关文档片段，交由 LLM 生成回答。命中率优先，延迟要求 <2s。

🔄

多轮对话

需要上下文记忆和意图跟踪。支持追问、澄清、话题切换，依赖对话状态管理（DSM）和历史轮次压缩。

🎫

工单流转

当 AI 无法解决时自动升级至人工。需识别「转人工」触发条件（置信度阈值、关键词匹配、用户情绪检测）并携带上下文。

实践建议：首期项目建议从 FAQ 问答切入，覆盖 80% 的高频问题后再扩展多轮对话能力。工单流转作为兜底机制贯穿始终，保障用户体验闭环。

1.2 目标用户画像

不同用户群体的表达习惯和容忍度差异显著，直接影响系统对「模糊查询理解能力」和「响应速度」的投入权重。

B 端企业用户有技术基础、问题专业度高、需精确回答"API 调用返回 403，已确认鉴权 token 有效"准确性 + 引用溯源

🎯

2.3 向量数据库选型

向量数据库是 RAG 的存储引擎，选型核心看数据规模、检索性能、部署方式和生态成熟度。

🗄️

Milvus（推荐）

支持十亿级向量，IVF + PQ 压缩大幅降内存。社区活跃，K8s 部署成熟。适合大规模生产环境。缺点：部署运维较重，需要 etcd + MinIO 依赖。

⚡

Qdrant（轻量首选）

Rust 编写，单机性能极强。支持 payload 过滤（元数据预筛选），API 简洁。百万级向量首选。Docker 一键部署，运维成本极低。

🐘

PGVector（已有 PG）

如果已经在用 PostgreSQL，PGVector 零额外运维成本。HNSW 索引性能不错，支持 SQL + 向量混合查询。适合中小规模（百万级以内）。

🧪

Chroma（原型验证）

纯 Python，pip install 即用。适合 PoC 阶段快速验证。但不支持分布式，数据量大后性能下降明显，不建议生产使用。

选型公式：向量数 < 100万 → Qdrant / PGVector ｜ 100万~1亿 → Milvus ｜ > 1亿 → Milvus 集群

2.5 RAG 框架对比

🔗

LangChain

生态最大，组件最多。Document Loader / Splitter / Retriever / Chain 全链路覆盖。适合需要灵活定制的团队。缺点：抽象层较多，调试有学习成本。

📖

LlamaIndex

专注 RAG 场景，数据摄入和索引设计更精细。支持多种 Index 结构（List / Tree / Keyword Table / Vector Store）。适合对检索质量有极致要求的场景。

🎨

Dify

低代码可视化平台，拖拽式编排。适合非技术团队快速搭建 PoC，也支持自定义代码扩展。缺点：深度定制受限，黑盒程度较高。

选型建议：团队能力强 + 需要深度定制 → LangChain / LlamaIndex；快速验证 + 非技术团队 → Dify。两者并不互斥，可以先用 Dify 验证 MVP，再迁移到 LangChain 做生产化。

3.3 文本分块策略（核心）

分块是数据清洗中影响检索质量最大的单一因素。块太大 → 检索精度下降、Token 浪费；块太小 → 语义碎片化、上下文丢失。

📐

固定长度分块（Fixed Size）

按固定 Token 数切分（如 512 tokens），设置 10-20% 重叠避免语义断裂。简单可靠，适合初期快速上线。缺点：可能切断句子和段落。

🧩

语义分块（Semantic Splitting）

按自然段落/标题层级切分，保持语义完整。利用文档结构（Markdown 标题、Word Heading）作为分块边界。检索质量最优但实现复杂。

🌳

递归分块（Recursive Splitting）

LangChain RecursiveCharacterTextSplitter：按分隔符优先级递归切分（\n\n → \n → 。 → 空格 → 字符）。兼顾语义和长度约束。

📊

父子分块（Parent-Child）

小块检索（精准命中），大块返回（完整上下文）。检索用 256-token 子块，召回后扩展到 1024-token 父块送入 LLM。两全其美。

python 
# LangChain 递归分块 + 父子分块策略
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain.retrievers import ParentDocumentRetriever
from langchain.storage import InMemoryStore

# 子块：用于精准检索
child_splitter = RecursiveCharacterTextSplitter(
    chunk_size=400,           # 子块 400 字符
    chunk_overlap=50,         # 50 字符重叠
    separators=["\n\n", "\n", "。", "！", "？", "；", " ", ""]
)

# 父块：提供完整上下文
parent_splitter = RecursiveCharacterTextSplitter(
    chunk_size=2000,          # 父块 2000 字符
    chunk_overlap=200,
)

# 检索时命中子块 → 自动映射到父块 → 父块送入 LLM
# 效果：精准检索 + 完整上下文，两全其美
最佳实践：中文场景建议 chunk_size = 300~500 字符（约 200~350 tokens），overlap = 10%~15%。Embedding 模型最大输入 512 tokens 时，超过的块会被截断丢失信息。

3.4 去重与去噪

知识库中常见的噪音：重复文档、模板化内容、过期信息、格式残留。不清理会降低检索精度并干扰 LLM 生成。

🔁

文档级去重

文件 Hash 去重（MD5/SHA256）。版本更新时用「内容指纹」判断是否真正变化，避免重复入库旧版本。

🧬

块级去重

MinHash + LSH 近似去重，找出语义相似的重复块。Jaccard 相似度 > 0.8 的块只保留最新版本。

🔇

噪音过滤

规则过滤：去除纯符号/数字块、长度 < 20 字的碎片、模板化免责声明、页眉页脚残留。

python 
# MinHash + LSH 近似去重
from datasketch import MinHash, MinHashLSH

def create_minhash(text, num_perm=128):
    m = MinHash(num_perm=num_perm)
    for word in text.split():    # 按 word shingling
        m.update(word.encode('utf-8'))
    return m

lsh = MinHashLSH(threshold=0.85, num_perm=128)  # Jaccard > 0.85 视为重复

for idx, chunk in enumerate(all_chunks):
    mh = create_minhash(chunk.text)
    result = lsh.query(mh)
    if result:    # 找到相似块 → 去重
        print(f"Chunk {idx} 与 {result} 相似，跳过")
    else:
        lsh.insert(str(idx), mh)    # 唯一块 → 入库

3.5 元数据标注

元数据是检索时的「预过滤器」，可以在向量检索前先按条件缩小范围，大幅提升检索精度和速度。

元数据字段示例用途
source"product_manual_v3.pdf"回答溯源、来源可信度判断
category"售后/退货/退款流程"按业务类目预过滤，缩小检索范围
created_at / updated_at"2024-03-15"时效性控制：优先返回最新内容
language"zh-CN"多语言场景下按语言过滤
access_level"public" / "internal"权限控制：不同用户看到不同知识
doc_type"FAQ" / "policy" / "manual"不同文档类型的召回权重调整
chunk_index"parent_007_child_003"父子块映射、上下文扩展
实战技巧：利用元数据做「条件检索」是提升精度的利器。例如用户问"退货流程"，先用 metadata.category="售后" 预过滤，再在售后类目内做向量检索，Top-5 命中率可提升 20-30%。

4.2 混合检索（Hybrid Search）

关键词检索（BM25）擅长精确匹配（产品型号、专有名词、错误代码），向量检索擅长语义理解（同义表达、模糊提问）。两者融合互补，覆盖更多查询场景。

🔤

BM25 关键词检索

基于词频和逆文档频率。对"iPhone 15 Pro Max 256G 退货"这类包含精确实体的查询效果极佳。Elasticsearch / OpenSearch 原生支持。

🧠

Dense 向量检索

语义级匹配，"手机买了能退吗"能召回"退货退款政策"。对口语化、同义词、跨语言查询有天然优势。

RRF 融合算法（Reciprocal Rank Fusion）

将多路检索结果按排名融合，无需归一化分数，简单有效：

RRF Score = Σ ( 1 / (k + ranki) )    k 通常取 60
python 
# 混合检索：BM25 + Dense Vector + RRF 融合
from langchain.retrievers import EnsembleRetriever
from langchain_community.retrievers import BM25Retriever

# 1. BM25 关键词检索
bm25_retriever = BM25Retriever.from_documents(all_chunks)
bm25_retriever.k = 20   # 召回 Top-20

# 2. 向量检索
vector_retriever = vector_store.as_retriever(
    search_type="similarity",
    search_kwargs={"k": 20, "filter": {"category": "售后"}}
)

# 3. RRF 融合（权重可调）
ensemble_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, vector_retriever],
    weights=[0.3, 0.7]    # 向量权重更高，因为客服场景语义匹配更重要
)

# 4. 融合后取 Top-20 交给 Reranker 精排
results = ensemble_retriever.invoke("买了东西怎么退货")
效果对比：纯向量 Recall@5 ≈ 68% → 混合检索 Recall@5 ≈ 82% → 混合 + Rerank Recall@5 ≈ 91%。投入产出比极高，是 RAG 优化的第一优先级。

4.3 重排序（Reranking）

Embedding 检索是双塔模型（Query 和 Doc 独立编码），速度快但精度有限。Reranker 是交叉编码器（Cross-Encoder，Query 和 Doc 联合编码），精度高但速度慢。两阶段架构：先用向量检索粗筛 Top-50，再用 Reranker 精排 Top-5。

🏗️

双塔模型（Embedding）

Query → Vector，Doc → Vector，计算余弦相似度。可预计算 Doc 向量，检索速度极快（ms 级）。但 Query 和 Doc 无交互，容易漏召回同义不同表述。

🔬

交叉编码器（Reranker）

输入 [Query, Doc] 对，输出相关性分数。Query 和 Doc 深度交互，精度远超双塔。但无法预计算，每对都要推理，适合精排少量候选。

python 
# 使用 bge-reranker-v2-m3 精排
from FlagEmbedding import FlagReranker

reranker = FlagReranker('BAAI/bge-reranker-v2-m3', use_fp16=True)

# 混合检索得到的 Top-50 候选
candidates = ensemble_retriever.invoke(user_query)  # 50 条

# Reranker 精排
pairs = [[user_query, doc.page_content] for doc in candidates]
scores = reranker.compute_score(pairs, normalize=True)

# 取 Top-5 交给 LLM 生成
top_5 = sorted(zip(candidates, scores), key=lambda x: x[1], reverse=True)[:5]
context = "\n\n".join([doc.page_content for doc, score in top_5])
延迟控制：Reranker 对 50 条候选的推理时间约 100-300ms（GPU）。如果延迟敏感，减少候选数到 20-30 条。CPU 部署建议用更小的 reranker-v2-gemma 或 ONNX 量化版本。

4.4 Query 改写与扩展

用户原始查询往往模糊、口语化、缺乏关键词。在检索前对 Query 进行改写和扩展，能显著提升召回率。

🔄

Query Rewriting

用 LLM 将口语化查询改写为更利于检索的形式。"东西坏了找谁" → "产品故障报修联系渠道与流程"。

🔀

Multi-Query

用 LLM 生成同一意图的多个变体查询，多路并行检索后融合。覆盖不同表述方式的知识块。

🎭

HyDE

Hypothetical Document Embedding：先让 LLM 生成一个假设性答案，用答案的向量去检索。因为答案和文档的语义空间更接近。

python 
# Multi-Query 扩展示例
from langchain.retrievers.multi_query import MultiQueryRetriever
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# 自动生成 3 个查询变体并并行检索
multi_retriever = MultiQueryRetriever.from_llm(
    retriever=vector_retriever,
    llm=llm
)

# 原始查询: "退货"
# LLM 生成变体:
#   1. "商品退货退款流程与时效"
#   2. "如何申请退货 需要什么条件"  
#   3. "七天无理由退货政策说明"
# → 三路并行检索 → RRF 融合 → 候选集更全面

results = multi_retriever.invoke("退货")

4.5 其他召回优化技巧

📦

上下文压缩

检索到的长文本用小模型先做摘要/提取，只把最相关的句子送入 LLM。LangChain ContextualCompressionRetriever 可自动实现，节省 50%+ Token。

🗂️

时间衰减权重

对有时效性的知识（政策、价格），在 RRF 融合时加入时间衰减因子。越新的文档权重越高，避免返回过期信息。

⭐

用户反馈加权

根据用户点赞/踩的行为调整文档权重。被多次确认的文档在后续检索中排序靠前，实现自学习优化。

🚫

负面过滤

维护一个「已知无效」文档列表（旧版本、已废止政策），检索时直接排除。减少噪音干扰。

📈 召回优化效果总结

基准（纯向量检索）Recall@5 = 65% → 加混合检索 = 82% → 加 Reranker = 91% → 加 Multi-Query = 94% → 加上下文压缩 = 95%+。每一步提升都有明确 ROI，建议按此顺序逐步迭代。

5 📊 效果评测

没有度量就没有优化。效果评测是 RAG 系统持续迭代的「仪表盘」，需要建立从离线评测到在线监控的完整体系。

5.1 评测体系全景

🖥️

离线评测（Offline）

在标注好的测试集上运行系统，计算自动化指标。用于版本对比、参数调优、回归测试。每次迭代后跑全量测试集，确保不退化。

📡

在线评测（Online）

生产环境的实时监控。用户隐式反馈（是否追问、是否转人工、会话时长）+ 显式反馈（点赞/踩、评分）。用于发现 Bad Case。

5.2 自动评测指标

自动评测分为检索阶段和生成阶段两部分，分别衡量「找得准不准」和「答得好不好」。

🔍 检索阶段指标

指标公式含义目标值
Recall@K命中的相关文档数 / 全部相关文档数Top-K 中召回了多少比例的正确答案≥ 90%
Precision@K命中的相关文档数 / KTop-K 中有多少是真正相关的≥ 70%
MRR1 / 第一个相关文档的排名正确答案排在越靠前分数越高≥ 0.8
NDCG@KDCG / iDCG（考虑位置折扣）综合考虑相关性和排序位置的归一化指标≥ 0.85
Hit Rate有命中的查询数 / 总查询数多少比例的查询至少召回了 1 个相关文档≥ 95%

✍️ 生成阶段指标

指标说明适用场景局限
BLEUn-gram 精确匹配率有标准答案的精确匹配不适合语义评测，同义表达得分低
ROUGEn-gram 召回率（侧重覆盖）摘要类任务的覆盖度评估同 BLEU，依赖字面匹配
Faithfulness回答是否忠实于检索内容检测幻觉（Hallucination）需要 LLM 做评判
Answer Relevance回答与问题的相关性检测答非所问需要 LLM 做评判
Context Relevance检索内容与问题的相关性评估检索质量需要 LLM 做评判
重要提醒：BLEU/ROUGE 是机器翻译时代的指标，不适合评测 RAG 生成质量。客服场景的答案是开放式的，同义表达很多。应优先使用基于 LLM 的评测框架（RAGAS / TruLens），从 Faithfulness、Answer Relevance、Context Relevance 三个维度评估。

5.3 RAGAS 评测框架

RAGAS（RAG Assessment）是目前最主流的 RAG 自动评测框架，用 LLM 作为裁判，从三个维度自动打分：

🎯

Context Precision

检索到的上下文中，有多少比例真正与问题相关。衡量检索的精确度。分数低 → 检索噪音多 → 需要优化分块或加 Reranker。

📖

Faithfulness

生成的回答中，有多少比例的陈述能在检索到的上下文中找到支撑。衡量幻觉率。分数低 → LLM 在编造 → 需要优化 Prompt 或换模型。

💬

Answer Relevance

生成的回答与原始问题的相关程度。衡量答非所问。分数低 → 理解偏差 → 需要优化意图识别或 Query 改写。

python 
# RAGAS 自动评测
from ragas import evaluate
from ragas.metrics import (
    context_precision,
    faithfulness,
    answer_relevancy,
    context_recall,
)
from datasets import Dataset

# 构建评测数据集
eval_data = {
    "question":     ["退货流程是什么？", "API 报错 403 怎么解决？"],
    "answer":       [generated_answer_1,  generated_answer_2],
    "contexts":     [retrieved_docs_1,     retrieved_docs_2],
    "ground_truth": ["1. 进入订单页 2. ...", "检查 token 权限..."],
}
dataset = Dataset.from_dict(eval_data)

# 运行评测（需要 LLM 作为裁判）
result = evaluate(
    dataset,
    metrics=[context_precision, faithfulness, answer_relevancy, context_recall],
)
print(result)
# {'context_precision': 0.85, 'faithfulness': 0.92,
#  'answer_relevancy': 0.88, 'context_recall': 0.79}

5.4 人工评测维度

自动指标无法完全替代人工判断。生产级系统必须有定期人工抽检机制，从以下维度逐条评分（1-5 分）：

维度定义1 分（差）5 分（优）
相关性回答是否切题完全答非所问精准回答了用户问题
准确性信息是否正确有明显错误信息完全准确可验证
完整性回答是否充分只回答了部分问题覆盖全部子问题
流畅性语言是否通顺语法错误/逻辑混乱表达自然专业
安全性是否有有害内容泄露隐私/有偏见安全合规无风险
可操作性用户能否据此行动太抽象无法执行步骤清晰可执行
实施建议：每周从生产日志中随机抽取 100 条对话，由 2-3 名标注员独立打分。计算标注一致性（Cohen's Kappa），低于 0.7 时需要校准标准。将 Bad Case 反馈到知识库和 Prompt 优化中，形成闭环。

5.5 评测数据集构建

好的评测数据集 = 真实查询 + 标准答案 + 相关文档标注。构建方法分三个来源：

📜

历史日志挖掘

从客服系统历史对话中提取高频问题，人工标注标准答案。最贴近真实分布，但需要脱敏处理。

🤖

LLM 合成生成

给 LLM 知识库文档，让它生成可能的用户问题和标准答案。快速扩充数据量，但分布可能偏离真实。

👥

人工编写

由业务专家编写典型场景和边界 Case。质量最高但成本高，适合覆盖关键路径和极端情况。

数据集设计原则：① 覆盖所有意图类别，按真实分布加权 ② 包含「应该转人工」的负面 Case ③ 包含同义不同表述（测试语义理解） ④ 包含多轮对话（测试上下文记忆） ⑤ 定期更新，保持与业务同步。

★ 🏁 总结与路线图

构建一个生产级 RAG 智能客服不是一次性工程，而是持续迭代的过程。以下是推荐的落地路线图：

1️⃣

MVP 阶段（1-2 周）

FAQ 单轮问答 + 纯向量检索 + 小模型生成。验证核心链路跑通，建立评测基线。

2️⃣

增强阶段（2-4 周）

加混合检索 + Reranker + 元数据过滤。Recall@5 提升至 90%+，上线 A/B 测试。

3️⃣

多轮阶段（4-8 周）

加意图识别 + 对话状态管理 + Query 改写。支持追问和上下文记忆，转人工兜底。

4️⃣

优化阶段（持续）

在线监控 + Bad Case 闭环 + 用户反馈加权 + 知识库自动更新。建立持续优化飞轮。

核心心法：RAG 系统的优化 80% 在数据（分块策略 + 知识库质量），20% 在模型（LLM 选型 + Prompt）。不要在模型调优上花太多时间，先把数据和检索做扎实，效果提升立竿见影。
