01 通信协议总览

智能体系统中，通信协议决定了消息如何在 Agent、服务端、客户端之间流动。不同场景对延迟、方向性、连接持久性有着截然不同的需求，理解每种协议的本质特征是架构选型的基础。

为什么需要多种通信协议？

智能体系统不是单一的请求-响应模型。一个完整的 Agent 系统可能同时包含：用户与 Agent 的实时对话（需要流式输出）、Agent 之间的协作通信（需要双向消息）、Agent 向监控面板推送状态（需要单向推送），以及边缘设备的遥测数据上报（需要轻量协议）。每种场景对通信协议的要求不同：

⚡
实时性

LLM 流式输出需要逐 Token 推送，传统 HTTP 轮询延迟过高

🔄
方向性

服务端推送 vs 客户端推送 vs 双向通信，方向决定协议

🔗
连接管理

短连接 vs 长连接 vs 持久连接，影响资源消耗与延迟

📱
资源约束

IoT 设备 CPU/内存/带宽受限，需要轻量级协议

02 普通HTTP通信

HTTP 是互联网最基础的通信协议，采用请求-响应模式。它是所有 Web API 的基石，但在实时性和双向通信方面存在固有局限。

🔄 请求-响应模型

HTTP（HyperText Transfer Protocol）是一种无状态的、基于请求-响应的协议。客户端发起请求，服务端返回响应，连接随后关闭（HTTP/1.1 默认 keep-alive 可复用连接，但仍是请求-驱动模式）。

✅ 核心特点

1
无状态协议

每个请求独立，服务器不保留客户端状态（通过 Cookie/Token 实现会话）

2
请求-驱动模式

永远是客户端先发起请求，服务端只能被动响应

3
文本协议

HTTP/1.x 是文本协议，Header 明文可读；HTTP/2 引入二进制分帧

⚠️ 在Agent场景中的局限

🚫 局限
  • 无法服务端主动推送（需轮询）
  • 每次请求 Header 开销大
  • 轮询导致延迟与资源浪费
  • 不支持流式输出（HTTP/1.x）
  • 无法维持双向实时通信
✓ 适用
  • RESTful API 调用
  • Agent 工具调用 / 函数调用
  • RAG 知识库查询
  • 非实时数据获取
  • 幂等的 CRUD 操作

🔄 轮询（Polling）— HTTP 的实时性补偿方案

在需要"伪实时"更新的场景中，HTTP 可以通过轮询模拟实时性。但这带来了额外的延迟和资源开销：

🔄
短轮询

客户端定时发请求查结果。延迟=轮询间隔，间隔越短服务器压力越大。

⏳
长轮询

服务端hold住请求直到有数据才返回。延迟更低，但占用服务端线程。

📦
HTTP 流式

利用Transfer-Encoding: chunked分块传输，实现伪流式输出。

注意：轮询方案在 Agent 场景下有硬伤——LLM 推理可能需要 10-30 秒，轮询间隔不好定。短轮询浪费请求，长轮询占用连接。这正是 SSE / WebSocket 存在的理由。

💻 HTTP 调用示例（Agent 工具调用场景）

// 前端 → Agent 后端 → LLM API 的典型 HTTP 调用链
const response = await fetch('/api/agent/chat', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    message: "分析今天的股票行情",
    sessionId: "sess_abc123"
  })
});

const result = await response.json();
// 等待整个响应完成才能拿到结果 — 无法流式输出
console.log(result.reply);
// ⏳ 如果 LLM 推理需要 20s，用户要白屏等待 20s
03 WebSocket 协议

WebSocket 是唯一提供全双工通信的 Web 协议。一次握手后，客户端和服务端可以在同一连接上随时互发消息，是实时 Agent 协作通信的首选。

🔌 全双工通信机制

WebSocket 通过 HTTP 升级握手建立连接，随后在同一 TCP 连接上切换到 WebSocket 协议（ws:// 或 wss://），实现双向实时通信。

🔑 核心特征

🔄
全双工

双方可同时发送和接收，无需等待对方

🔗
持久连接

一次握手后连接持续，避免反复建立 TCP

📊
低开销

数据帧头仅 2-14 字节，远小于 HTTP Header

⚡
低延迟

消息即时推送，无需轮询等待

📋 适用场景

🤖 多 Agent 实时协作 💬 聊天 / 对话系统 📊 实时数据看板 🎮 多人协同编辑 🔔 即时通知推送 📈 金融实时行情 🖥️ 远程终端
Agent 场景：多 Agent 系统中，Agent 之间需要频繁交换中间结果、状态更新和中断信号，WebSocket 的全双工特性使其成为 Agent-to-Agent（A2A）通信的理想选择。

🆚 WebSocket vs HTTP 的关键差异

对比维度 HTTP WebSocket
通信方向单向（客户端→服务端→客户端）全双工（双向同时）
连接生命周期短连接（请求-响应-可关闭）持久连接（握手后一直保持）
谁可以主动发消息只有客户端能发起请求双方都可以随时发送
协议层HTTP/1.x 文本协议基于 HTTP 升级，之后切到 WS 二进制帧
数据帧头开销每次请求 ~200-800 字节 Header2-14 字节帧头
实时延迟高（取决于轮询间隔）极低（毫秒级推送）
服务端推送能力无（需轮询 / 长轮询模拟）原生支持
代理/防火墙兼容极好（所有网络设备都支持）部分代理可能不支持 Upgrade
断线重连天然支持（每次都是新请求）需手动实现（心跳+重连逻辑）
状态管理无状态，每次请求需带认证有状态，握手时认证后保持会话

💻 WebSocket 代码示例

// 浏览器端 WebSocket — Agent 实时对话
const ws = new WebSocket('wss://api.agent.com/ws/chat');

ws.onopen = () => {
  console.log('连接已建立');
  ws.send(JSON.stringify({
    type: 'chat',
    message: '分析今日A股市场'
  }));
};

ws.onmessage = (event) => {
  const data = JSON.parse(event.data);
  if (data.type === 'token') {
    // 逐 Token 流式渲染 LLM 输出
    appendToken(data.content);
  } else if (data.type === 'tool_call') {
    // Agent 正在调用工具（如搜索新闻）
    showToolCall(data.tool, data.args);
  } else if (data.type === 'done') {
    console.log('Agent 回复完成');
  }
};

ws.onclose = () => console.log('连接已关闭');
ws.onerror = (err) => console.error('连接异常', err);

// 用户可随时发送消息（全双工）
function sendInterrupt() {
  ws.send(JSON.stringify({ type: 'interrupt' }));
}
// Node.js 后端 WebSocket 服务（ws 库）
const { WebSocketServer } = require('ws');
const wss = new WebSocketServer({ port: 8080 });

wss.on('connection', (ws, req) => {
  // 握手时鉴权
  const token = new URL(req.url, 'ws://localhost').searchParams.get('token');
  if (!verifyToken(token)) return ws.close();

  ws.on('message', async (raw) => {
    const msg = JSON.parse(raw);

    if (msg.type === 'chat') {
      // 调用 LLM 并流式推送每个 Token
      const stream = await llmClient.streamChat(msg.message);
      for await (const chunk of stream) {
        ws.send(JSON.stringify({
          type: 'token',
          content: chunk.content
        }));
      }
      ws.send(JSON.stringify({ type: 'done' }));
    }
  });

  // 心跳保活
  const heartbeat = setInterval(() => {
    if (ws.readyState === WebSocket.OPEN) ws.send(JSON.stringify({ type: 'ping' }));
  }, 30000);

  ws.on('close', () => clearInterval(heartbeat));
});

⚠️ WebSocket 的踩坑点

代理/防火墙不兼容
高频
企业网络代理可能不支持 HTTP Upgrade，导致连接失败。需配合 wss:// + TLS 透传或使用 SSE 作为降级方案。
连接管理复杂
中频
需自行实现心跳保活、断线重连、连接池管理、超时清理。没有 HTTP 那种"请求完就释放"的简单模型。
04 SSE (Server-Sent Events)

SSE 是基于 HTTP 的单向推送协议。服务端可以在一条长连接上持续向客户端推送事件流。它是 LLM 流式输出和 Agent 状态推送的最常用方案。

📡 单向推送机制

SSE 利用 HTTP 长连接实现服务端到客户端的单向推送。客户端通过 EventSource API 建立连接，服务端以 text/event-stream 格式持续推送事件。

🔑 SSE 核心特征

1
基于 HTTP 协议

不需要协议升级，走标准 HTTP 通道，防火墙/代理天然兼容

2
单向推送

服务端→客户端单向。客户端如需发送数据，走独立 HTTP 请求

3
自动重连

浏览器原生 EventSource 断线自动重连，无需手写重连逻辑

4
文本格式

事件流是纯文本（UTF-8），不支持二进制数据

🆚 SSE vs WebSocket 对比

维度SSEWebSocket
通信方向单向（S→C）全双工
底层协议HTTPHTTP 升级后 WS
断线重连浏览器自动重连需手动实现
代理兼容极好可能有问题
数据格式仅文本文本+二进制
浏览器 APIEventSourceWebSocket
连接数限制6 conn/域(HTTP/1)无此限制
最佳场景LLM 流式输出双向实时协作

📋 SSE 适用场景

🤖
LLM 流式输出

逐 Token 推送 LLM 回复，OpenAI API stream:true 就是 SSE

📊
Agent 执行状态

"正在搜索… 正在分析… 正在生成…"等进度推送

🔔
通知/告警

服务端主动推送通知，无需客户端轮询

📈
实时数据流

股票行情、日志流、监控指标推送

为什么 OpenAI 选 SSE 而不是 WebSocket？ 因为 LLM 流式输出是典型的"服务端→客户端单向推送"场景——用户发一次请求，服务端逐 Token 回传。不需要全双工，SSE 的自动重连和 HTTP 兼容性反而是优势。

💻 SSE 代码示例

// 方式1: EventSource API — 最简单
const evtSource = new EventSource('/api/agent/stream?msg=分析A股');

// 监听默认 message 事件
evtSource.onmessage = (e) => {
  const data = JSON.parse(e.data);
  if (data.done) {
    evtSource.close(); // 主动关闭
    return;
  }
  appendToken(data.content); // 渲染 Token
};

// 监听自定义事件
evtSource.addEventListener('tool_call', (e) => {
  const tool = JSON.parse(e.data);
  showToolCall(tool.name, tool.args);
});

evtSource.addEventListener('done', () => {
  evtSource.close();
});

// 断线自动重连 — EventSource 内置
// 但注意：重连会重新发 GET 请求，需用 Last-Event-ID 处理续传
// 方式2: fetch + ReadableStream — 支持 POST 请求
// EventSource 只支持 GET，POST 场景需用 fetch 模拟 SSE
const response = await fetch('/api/agent/chat', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ message: '分析A股' })
});

const reader = response.body.getReader();
const decoder = new TextDecoder();
let buffer = '';

while (true) {
  const { done, value } = await reader.read();
  if (done) break;

  buffer += decoder.decode(value, { stream: true });
  const lines = buffer.split('\n');
  buffer = lines.pop(); // 保留不完整的行

  for (const line of lines) {
    if (line.startsWith('data: ')) {
      const data = JSON.parse(line.slice(6));
      appendToken(data.content);
    }
  }
}
05 Spring 框架中的 SseEmitter

SseEmitter 是 Spring MVC 对 SSE 的封装。它允许 Controller 方法返回一个可异步写入的 emitter，在独立线程中逐步推送事件，是 Java 后端实现 Agent 流式输出的标准方案。

🍃 SseEmitter 在 Spring MVC 中的角色

SseEmitter 是 Spring 4.2+ 提供的 SSE 支持类。它将 SSE 的底层细节（HTTP 响应头、事件格式、连接管理）封装起来，开发者只需关注何时推送什么数据。

🔄 SseEmitter 生命周期管理

SseEmitter 的生命周期是理解它的关键：创建 → 在异步线程中写入 → 完成/超时/出错 → 清理。每个阶段都有对应的回调和配置。

1
创建 Emitter

new SseEmitter(0L) — 参数为超时时间（毫秒），0L 表示永不超时。通常设为 30000-120000ms。

2
注册回调

通过 onCompletion、onTimeout、onError 注册生命周期回调，用于资源清理。

3
异步写入事件

在独立线程/线程池中调用 emitter.send() 逐个推送事件。Spring 会自动将事件写入 HTTP 响应流。

4
完成与清理

推送完毕调用 emitter.complete() 关闭连接。如遇异常调用 completeWithError()。超时则由 Spring 自动关闭。

💻 Spring Boot + SseEmitter 完整示例

// ──────────────────────────────────────────
// 1. Controller — 接收请求，返回 SseEmitter
// ──────────────────────────────────────────
@RestController
@RequestMapping("/api/agent")
public class AgentController {

    @Autowired
    private AgentService agentService;

    @GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public SseEmitter streamChat(@RequestParam String message) {
        // 创建 Emitter，超时 120 秒（LLM 推理可能较慢）
        SseEmitter emitter = new SseEmitter(120_000L);

        // 注册生命周期回调
        emitter.onCompletion(() -> log.info("SSE 连接完成"));
        emitter.onTimeout(() -> {
            log.warn("SSE 连接超时");
            emitter.complete();
        });
        emitter.onError(ex -> log.error("SSE 连接异常", ex));

        // 异步执行 Agent 逻辑（不阻塞 Tomcat 线程）
        agentService.executeAsync(message, emitter);

        return emitter; // 立即返回，Spring 保持连接
    }
}

// ──────────────────────────────────────────
// 2. Service — 异步推送事件
// ──────────────────────────────────────────
@Service
public class AgentService {

    @Async // 异步线程执行，不阻塞 Controller 线程
    public void executeAsync(String message, SseEmitter emitter) {
        try {
            // 推送"开始思考"事件
            emitter.send(SseEmitter.event()
                    .name("status")
                    .data("thinking"));

            // 调用 LLM 流式 API，逐 Token 推送
            Flux<String> tokenFlux = llmClient.streamChat(message);
            tokenFlux.doOnNext(token -> {
                emitter.send(SseEmitter.event()
                        .name("token")
                        .data(new TokenPayload(token)));
            }).doOnComplete(() -> {
                // 推送完成事件
                emitter.send(SseEmitter.event()
                        .name("done")
                        .data("[DONE]"));
                emitter.complete(); // 关闭连接
            }).doOnError(e -> {
                emitter.send(SseEmitter.event()
                        .name("error")
                        .data(e.getMessage()));
                emitter.completeWithError(e);
            }).subscribe();

        } catch (Exception e) {
            emitter.completeWithError(e);
        }
    }
}

📋 实际应用场景

🤖 LLM 流式对话 📊 Agent 执行进度 🔍 RAG 检索过程展示 📝 长任务异步通知 🔔 实时告警推送 📈 数据变更通知

⚠️ SseEmitter 踩坑点

线程池耗尽：SseEmitter 异步执行默认用 SimpleAsyncTaskExecutor，每次创建新线程。生产环境必须自定义 @Bean ThreadPoolTaskExecutor，否则高并发下线程爆炸。
Tomcat 异步超时：Spring MVC 异步请求默认超时 30s。需在 application.yml 配置 spring.mvc.async.request-timeout=-1 或设为足够大的值。
连接泄漏：如果 emitter 永不 complete 也不 timeout，连接会一直占用。务必在 finally 中调用 complete()。

🔧 Spring Boot 异步配置

// application.yml
spring:
  mvc:
    async:
      request-timeout: -1  # 禁用 MVC 异步超时（由 SseEmitter 自己控制）

// 配置异步线程池 — 避免线程爆炸
@Configuration
@EnableAsync
public class AsyncConfig implements AsyncConfigurer {

    @Override
    public Executor getAsyncExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(5);
        executor.setMaxPoolSize(50);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("agent-sse-");
        executor.initialize();
        return executor;
    }
}
06 物联网通信协议

在边缘智能体（Edge Agent）和设备遥测场景中，传统 HTTP/WebSocket 协议过重。MQTT 和 CoAP 是专为受限设备和不可靠网络设计的轻量级协议。

📡 MQTT — 消息队列遥测传输

MQTT 是基于 TCP 的发布-订阅模式轻量消息协议，专为网络带宽有限、设备资源受限的场景设计。

核心特性
📦
极小协议头

固定头仅 2 字节，最小化带宽消耗

🔄
发布-订阅

发送方与接收方完全解耦

📊
QoS 三级

0=最多一次, 1=至少一次, 2=恰好一次

💾
遗嘱消息

设备离线时 Broker 自动通知订阅者

🔌
保持连接

心跳机制保持长连接，检测断线

📝
持久会话

重连后恢复订阅，不丢消息

IoT Agent 场景：边缘设备上的轻量 Agent 通过 MQTT 上报传感器数据到 Broker，云端 Agent 订阅主题接收数据并做决策，再将控制指令通过另一个主题下发。

📱 CoAP — 受限应用协议

CoAP 是基于 UDP 的 RESTful 轻量协议，专为极低功耗设备和不可靠网络设计。可以理解为"UDP 版的 HTTP"。

核心特性
⚡
基于UDP

无连接，极低开销，无需建立/断开连接

📋
RESTful

GET/POST/PUT/DELETE，语义与 HTTP 一致

🔄
可靠传输

Confirmable 模式提供 ACK + 重传机制

👁
Observe

订阅资源变更，Server 主动推送更新

🔍
资源发现

/.well-known/core 自动发现设备资源

📦
超紧凑

头部仅 4 字节，比 HTTP 头小 50-100 倍

CoAP vs MQTT 区别：MQTT 是发布-订阅模式（需 Broker 中转），CoAP 是请求-响应模式（端到端直连）。MQTT 适合一对多分发，CoAP 适合点对点资源操作。

08 选型决策指南

面对具体场景，如何从五大协议中做出正确选择？下面从场景需求出发，给出决策路径和推荐方案。

🧭 决策流程图

📋 场景-协议推荐矩阵

Web前端
LLM 对话流式输出
用户发一条消息，LLM 逐 Token 回复。单向推送，需断线重连。
推荐：SSE / Spring SseEmitter — 自动重连、HTTP 兼容、实现简单
多Agent
Agent 间实时协作
多个 Agent 互相交换中间结果、状态和中断信号，需要双向实时通信。
推荐：WebSocket — 全双工、低延迟、持久连接
API
工具调用 / RAG 查询
Agent 调用外部工具（搜索、数据库、API），请求-响应模式即可。
推荐：HTTP — 简单、通用、无状态、RESTful
IoT
边缘设备遥测上报
大量传感器持续上报数据到云端 Agent，网络不稳定，设备资源受限。
推荐：MQTT — 发布-订阅、QoS、遗嘱消息、极低开销
IoT
设备资源直接操作
Agent 直接控制传感器/执行器，读温度、开关灯，RESTful 语义。
推荐：CoAP — UDP 轻量、RESTful、Observe 推送
混合
Agent 全栈通信
前端←SSE→后端←HTTP→LLM, 后端←WebSocket→其他Agent, 后端←MQTT→边缘设备。
推荐：多协议组合 — 每层用最合适的协议

09 总结与速查

五大协议各有所长，没有"银弹"。理解每种协议的本质特征，才能在正确的场景做出正确的选择。

📌 一句话总结

📋
HTTP

请求-响应的基石。无状态、通用、简单。适合工具调用和 API 交互，不适合实时推送。

⚡
WebSocket

全双工实时通信。一次握手，双向随时发送。适合多 Agent 协作，但连接管理复杂。

📡
SSE

服务端单向推送。基于 HTTP，自动重连，实现简单。LLM 流式输出的首选。

📱
MQTT

IoT 消息总线。发布-订阅、QoS、遗嘱消息。适合大规模设备遥测数据汇聚。

💡
CoAP

IoT RESTful 协议。基于 UDP，超轻量。适合 Agent 直接操作设备资源。

🍃
SseEmitter

Spring 的 SSE 封装。异步推送、生命周期管理。Java 后端流式输出标准方案。
